# 为什么总是我先发现问题

写于 2026-10-05。回答你的问题：“不能一直是我发现问题、你再去解决。是我的思路太乱导致的吗？合同系统那个项目也是这样。”

## 结论

**主要不是你思路乱。** 是开发过程里少了三个环节，其中两个该由我补上，一个需要你配合。

你的直觉有一半是对的：有一类问题确实不该由你来发现。另一半需要分清：有一类问题只能在真实使用中发现，这在 Agent 开发里是正常的，不正常的是发现之后没有把它固定下来。

## 先看事实

把这个项目里出现过的问题按“谁先发现”列出来。

**你先发现的（约 20 个）：**

| 类别 | 问题 |
|---|---|
| A. 我没有按你的用法走一遍 | 草稿生成后要手动刷新才看得到；只能定时不能立即去发；审核通过后看不到文案；历史批次标题只显示“20…”；不知道在哪里给反馈；读图失败要重新建批次、重传照片；任务没有结束的出口；驳回不留原因 |
| B. 我只测了顺利的情况 | 上传非主页图片只报“无法识别”；连锁店有 12 家门店被判成“格式不对”；访问码输对了仍被拒；前端换了端口就连不上；所有审核按钮点了都报 422 |
| C. 需求没问清就动手 | 产品定位写错两次；改了路线却不重新生成；置顶笔记被算进活跃度；按店名搜索而不是按小红书号；人工修改没有被记录 |
| D. 只有真实使用才能发现 | 私信内容雷同；分档规则没有区分度 |

**我先发现的（约 8 个）：** 数据库临时文件被提交进了 Git；测试文件写进了真实上传目录；回复表单的默认值会把拒绝记成“想了解产品”；真实数据库里混着测试记录；定时提醒实际上不会触发；一处函数顺序错误；修改原因没有进入汇总；模型编造了“符合佛山本地客人的审美”。

## 这四类问题的性质不一样

| 类别 | 数量 | 该不该由你发现 | 责任 |
|---|---|---|---|
| A. 没按你的用法走一遍 | 8 | **不该** | 我 |
| B. 只测了顺利的情况 | 5 | **不该** | 我 |
| C. 需求没问清就动手 | 5 | 一半一半 | 我们两个 |
| D. 只有真实使用才能发现 | 2 | 该，但发现之后要固定下来 | 流程 |

A 和 B 加起来 13 个，占了大半。它们的共同点是：**我验证的是“我写的功能能不能运行”，而不是“你能不能把这件事做完”。**

举今天的例子。“草稿生成后要手动刷新”这个问题，批量初筛页面我测过，工作流页面我也测过，两个都是好的。但你的实际用法是从第一个页面走到第二个页面，这条跨页面的路我没走过。

## 三个缺失的环节

### 缺失一：动手之前没有“走查剧本”（需要你配合）

每次你提一个需求，我直接开始写。我们从来没有先对一遍：“做完之后，你会怎么用它，每一步应该看到什么。”

C 类问题全部出在这里。你说“生成私信”，我理解成“生成一段文字”；你心里想的是“按这家店的情况写、发的时候能准确找到这家店、我改了你要知道”。这些你觉得理所当然的事，没说出来，我也没问。

**这不是思路乱，是把脑子里的画面当成了已经说过的话。** 几乎所有提需求的人都会这样，所以才需要一个固定的动作把它逼出来。

### 缺失二：做完之后没有固定的全流程检查（该我做）

我每次只验证刚改的那一处。今天下午拆代码时，我才第一次写了一个从上传截图走到记录回复的完整检查，16 个检查点。它跑一遍不到一分钟。

如果这个检查三天前就有，A 类的大部分问题会在交给你之前被我自己撞上。

### 缺失三：发现的问题没有变成“以后自动检查”（该我做）

你指出一个问题，我修掉这一个，然后继续。同一类问题下次换个地方再出现。

今天后半天开始有了变化，可以对比：

| 做法 | 例子 |
|---|---|
| 只修这一个 | 历史批次标题显示不全 → 改这一行的样式 |
| 修掉这一类 | “Failed to fetch”查不出原因 → 加错误日志，以后所有后台错误都有记录 |
| 修掉这一类 | 函数顺序错误 → 加“加载整个后台”的测试，以后这类错自动被抓 |
| 修掉这一类 | 模型总用套话 → 加程序检查和自动重写，不再靠人眼 |

前一种做法下，问题数量不会减少。后一种才会。

## 那 Agent 开发到底该不该“边用边发现”

要分开说。

**不该的部分：** 页面逻辑、表单默认值、报错信息、跨页面的流程。这些是普通软件问题，和 Agent 无关，应该在交给你之前解决。A、B 两类都属于这里。

**该的部分：** 模型输出的质量。私信写得好不好、分档准不准，在真实使用之前谁也不知道。你今天发了 5 家、收到 2 个“不用了”之后，才看出内容雷同、把主动权交给了对方。这个发现不可能提前得到。

所以成熟的做法不是“不让你发现问题”，而是：

```text
普通软件问题  →  交付前由开发方用走查和自动检查拦住
模型质量问题  →  真实使用中发现  →  立刻变成一条评测标准  →  以后每次改动都自动检查这一条
```

你今天对私信的每一条批评，现在都变成了规则和检查。这一类问题的处理方式是对的。不对的是前一类也在靠你发现。

## 合同系统为什么也这样

我没看过那个项目，只能根据你的描述推断：如果也是“你提需求、AI 写、你试用、你指出问题”这个方式，那它缺的是同样三个环节，和你做的是什么项目无关。

换句话说，这是工作方式带来的，不是你个人的问题，也不是某个项目特有的。

## 从现在开始改什么

### 我这边（已经写进项目规则，以后每次都要做）

1. **动手之前先写走查剧本。** 三到六步：你会怎么操作，每一步应该看到什么。你看一眼，说“对”或者改。一分钟的事。
2. **交付之前跑全流程检查，并按剧本自己走一遍。** 汇报时写明走了哪几步、结果如何，而不只是“测试通过”。
3. **每修一个问题，问一句“这是哪一类”。** 能加自动检查的就加，让同类问题以后自己暴露。
4. **主动找问题，不等你报。** 每次开工先自己用几分钟走一遍主流程，把看到的别扭之处列给你。

### 你这边（建议）

1. **说需求时多说一句“我会怎么用它”。** 不用说技术，就说你的动作：“我传完图，点一下，然后去喝水，回来想直接看到草稿。”这一句能省掉一半的返工。
2. **看到问题时，不只说现象，再问一句“还有哪里会这样”。** 你今天其实已经在这么做了：从“这两个文件太大”直接跳到“现在就该拆，不然以后更难改”。这就是从一个问题看到一类问题。
3. **验收的时候按剧本走，而不是随便点。** 随便点能发现问题，但发现不了“该有却没有”的东西。

### 一个马上能做的

今天那个全流程检查脚本现在只在临时目录里。把它放进项目，每次改动后跑一遍。这一件事对“总是你先发现问题”的改善最直接。

## 一句话

你缺的不是清晰的思路，而是一个固定动作：**动手之前，把“做完之后怎么用”说出来。** 我缺的是另一个固定动作：**交给你之前，自己先像你一样用一遍。** 这两个动作补上，A、B、C 三类问题会少掉大半，剩下的 D 类是 Agent 开发里正常的、有价值的发现。
