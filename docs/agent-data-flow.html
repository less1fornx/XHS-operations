用你的项目理解 Agent 应用

从一张截图
到一条可复盘的业务结果

不是“把资料扔给 AI”。而是明确每一步谁提供数据、谁做判断、谁能否决，以及结果怎样回到系统。

核心地图 输入 → 检索（当前无 RAG）→ 程序规则 → LLM → 程序验证 → 人工修改与动作 → 结果反馈
01 / TOP-LEVEL DESIGN

Agent 顶层设计：从业务结果倒推系统

阶段验收、规则边界、输出都重要，但不是三个并列起点。先定义要改变的业务结果，再设计每个阶段如何产生可信、可验收的输出。

01 · WHY

定义业务结果与约束

明确谁的什么工作要变好、当前基线是什么、哪些代价不能接受。

本项目：让人工更有效地筛店、写首次沟通；但不自动抓取或发送。

02 · FLOW

画用户工作流与状态

把业务拆成真实阶段，标清进入条件、分支、等待人工、失败和恢复。

例如：上传 → 读图 → 批审 → 起草 → 审文案 → 人工发送 → 记录结果。

03 · CONTRACT

定义阶段输入与输出

每一步规定输入字段、输出结构、证据来源、版本和下游消费者。

例如：读图输出 ShopExtraction；起草输出结构化路线和文案。

04 · AUTHORITY

划分决策权与硬边界

明确模型能建议什么、代码必须强制什么、人工必须批准什么，以及模型永远不能做什么。

本项目：模型建议路线；代码管勿扰 / 配额 / 文案门禁；人决定路线和发送。

05 · EVIDENCE

定义验收证据与发布门槛

为每阶段选择可重复检查的质量指标、风险不变量、失败处理和上线条件。

先用固定案例和人工复核建立基线，不凭感觉设一个“准确率”。

06 · OPERATE

设计运行、监控与学习

记录每次调用、决策、修改、成本、延迟、错误和最终业务结果；提供回滚路径。

反馈是用于分析和批准新版本，不代表系统自动学会或自动改规则。

因此，你提到的三件事，正确关系是：

规则 / 边界定义系统允许的决策空间；阶段输出是节点之间的接口与可追踪工件；验收成果证明每个节点和整条流程达到目标。最终它们都服务于业务结果与风险约束。

每个阶段的“完成”至少要回答五项

输入契约需要哪些事实？缺失时是未知、失败还是人工补齐？
输出契约交付什么结构和证据？由哪个后续步骤消费？
质量门槛用哪些案例、指标或人工检查判定合格？
边界不变量哪些事情无论模型怎么说都不能发生？
失败与追踪如何停止 / 重试 / 升级人工？保存哪些 trace？
业务结果回复、意向、成交
AI 质量事实依据、路线、草稿
安全约束勿扰、导流、人工停点
运营效率耗时、修改率、采用率
系统可靠性失败率、延迟、成本
严谨的验收原则：不同层的指标不能互相代替。路线准确不代表草稿合规；草稿被用户接受不代表客户会回复；回复率也不能单独证明模型变好（名单和话术可能同时变化）。先固定输入和评估集，再比较版本。

套到当前项目：每阶段交付什么证据才算完成？

阶段阶段输出验收重点 / 不通过时
截图读取结构化店铺字段 + 不清楚字段字段能回指截图；看不清就标未知 / 人工核对，不把未知当成无关。
规则分档信号、档位、理由、规则版本相同输入和规则版本应得到相同结果；勿扰名单必须阻止进入触达候选。
路线与起草Schema 输出、证据引用、候选文案格式和引用有效；文案经过业务案例评测与程序政策检查；失败则展示原因并交人工，不伪装成功。
人工审核 / 发送最终路线、最终文本、修改原因、手动发送结果人工保有批准权；系统不能替人执行平台外部动作。
结果反馈回复与意向阶段 + 联系时快照结果能关联当时输入、文案和版本；用来评估，不让少量样本自动改规则。
不要先拍脑袋定所有数值门槛。先说明风险和业务目标，再用人工标注与固定样本建立基线；能用程序验证的硬约束单独设门槛，效果指标则在代表性数据上校准。

03 / DATA BOUNDARIES

七个边界：每一步交接什么？

1

输入了什么

含义：明确本次任务允许系统使用的原始资料。

项目例子：主页截图、笔记截图、人工补充的店铺情况和联系背景。

边界问题：给模型的是主页标题，还是整篇笔记？当前起草输入主要是识别后的字段和近期笔记标题，不等于完整笔记内容。
2

哪些信息被检索

含义：从更大的知识库挑出当前任务相关的资料。

当前项目：没有 RAG、embedding 或向量数据库；产品事实由配置文件直接提供。

将来可检索：已确认的产品卖点、经批准的话术经验、适用的规则版本。不能把未验证猜测包装成知识。
3

规则计算了什么

含义：对确定性条件用普通代码做明确判断，而不是让模型猜。

项目例子：程序用日期、价格和识别字段算信号、分档和排序；勿扰门禁先于文本模型。

注意：高 / 中 / 低目前是规则排序，不是经数据校准的回复率或成交概率。
4

模型返回了什么

含义：模型给候选判断与内容，不直接改数据库状态或发送消息。

项目例子：route、理由、业务摘要、证据引用、个性化点、草稿、不确定项。

模型给出的理由是可读说明，不是可审计的完整内部推理，也不是正确性的证明。
5

程序验证了什么

含义：把模型输出当成不可信输入，检查它是否符合可接受条件。

项目例子：JSON / Pydantic Schema、证据 ID 是否存在、勿扰门禁、评论与导流词检查。

Schema 合法 ≠ 内容真实；引用 ID 存在 ≠ 文案每句话都被证据证明。人工仍需核对。
6

人工改了什么

含义：记录模型草稿与人工最终版本之间的差异及修改原因。

项目例子：人工可改路线、编辑草稿、批准或驳回；已有修改原因记录的实现。

这些改动是偏好/监督信号，不会即时训练模型，也不应自动改规则或 Prompt。
7

结果如何反馈

含义：把真实回复、意向、成交或未成交关联回联系时的输入和版本。

项目例子：回复状态、对方需求标签、进展阶段、联系快照和最终发送文案。

反馈先用于分组统计与评估；样本不足时叫观察，不叫规律。策略变更需人工批准、对照评测和版本记录。
↔

为什么叫“边界”

每次交接都要讲清：数据从哪来、谁能修改、谁做决定、失败时停在哪里。

FDE 的价值之一，就是把模糊需求转成这些能实现、能测试、能追责的接口。
04 / TOKEN MECHANICS

Token 到底怎样变成回答？

以下是通用 LLM 的概念图。Qwen 的确切 tokenizer、内部层数和多模态编码方式由供应商实现，应用代码无法观察全部细节。

Prompt + JSON 输入→Tokenizer：文字 → token ID→模型计算→逐 token 生成→解码文字 / JSON→本地校验
A · ENCODE

文字切成 token

Token 是模型词表里的离散单元，不等于一个汉字或一个词。JSON 键名、标点、数字也占上下文。具体数量由 Qwen tokenizer 决定。

B · REPRESENT

ID 查成模型向量

每个 token ID 被映射成模型内部向量，再加入位置等信息。这是 LLM 自己处理输入的表示，不是 RAG 检索向量。

C · TRANSFORM

结合上下文更新表示

Transformer 多层计算，让当前 token 的表示融合上下文关系。可以理解为模型在处理“哪些输入信息与当前输出位置相关”。

D · SCORE

算下一个 token 的分布

模型对词表候选计算 logits，再形成概率分布；解码策略按配置选择下一个 token。温度较低会降低随机性，不保证确定正确。

E · GENERATE

循环生成直到结束

新 token 加回上下文，模型继续预测下一个 token，直到结束标记或长度限制。服务端再把 token 序列解码成 JSON 文本。

F · VALIDATE

应用解析并决定接不接受

本项目把返回内容交给 Pydantic 校验 Schema，再查证据引用；不通过就报错，不让不合格结果冒充成功。

两种 embedding 不要混淆：LLM 内部 token embedding 用于模型计算；RAG 的文本 embedding 用于相似度搜索。RAG 检索通常把找回的文字送给 LLM，不是把检索向量当 Prompt 传过去。
05 / RAG, HYPOTHETICAL

假设加入 RAG：向量先找资料，文字再进模型

离线：建立知识索引 假设设计

  1. 整理产品事实、已批准案例、有效规则；脱敏并标注来源、日期、版本和状态。
  2. 按主题切成适中片段（chunk），不要把无关章节混在一起。
  3. Embedding 模型把每个片段编码成向量。
  4. 保存“向量 + 原文 + 元数据”到向量索引。
知识片段 → embedding 模型 → [0.08, -0.21, …] + 原文 + 来源 / 版本

在线：检索后组装上下文 假设设计

  1. 根据店铺事实和当前任务形成查询。
  2. 用同一套 embedding 模型编码查询。
  3. 向量相似度搜索，按状态 / 场景等元数据过滤；可选 reranker 重排。
  4. 取回少量文字片段和来源，拼进 Prompt 后发给 LLM。
query → query vector → top-k 文档 → 过滤 / 重排 → 文本上下文 → LLM
关键纠正：Embedding 是“找相似资料”的索引表示，不是自动知识，也不会更新模型权重。检索错、资料过时或把假设标成事实，仍会让回答变差；所以 RAG 也需要来源、版本、权限和人工审核。
06 / TRACE ONE SHOP

跟一条店铺数据走一遍

假设截图里可见“西装定制”“全麻衬”“近期笔记标题”，程序读出这些内容。下面分清每一层的责任：

观察到的事实主页简介 + 全麻衬 + 笔记日期
→
程序计算面料信号 = yes；活跃信号按日期计算
→
模型候选建议路线、引用证据、生成草稿
程序验收结构正确？evidence_id 存在？文案触发拦截？
→
人工判断这句是否准确、像不像你、是否采用路线？
→
业务结果手动发送后记回复 / 意向 / 未回复

这个例子里，哪些不能混为一谈？

  • “全麻衬”是截图证据；“这家店可能重视面料”是解释；两者不是同一层事实。
  • “建议 DM”是模型建议；“允许进入队列”要通过程序规则和人工审核。
  • “文案被人工接受”是偏好信号；“对方回复”才是业务结果信号。
  • “回复了”不必然代表成交；结果要继续记录意向阶段，避免把指标混成一个成功率。
07 / YOUR FDE PATH

你偏产品，是做 FDE 的优势

你可以把方向理解成：产品型 FDE——先发现客户真实问题，再亲手搭出可运行的 AI 工作流，用使用结果验证产品有没有解决问题。

产品视角：做对问题目标客户是谁？痛点是什么？先优化筛选，还是先优化草稿？成功指标怎样定义？
FDE 视角：做成系统把输入、规则、模型接口、失败路径、人工控制和审计变成可运行实现。
AI 产品判断：选对职责判断哪步适合模型，哪步必须代码确定，哪里必须让人确认。
验证视角：证明有改善同一批案例对比 Prompt 版本；把人工修改和回复结果分开看。
① 输入边界：模型这次到底看到了什么？漏了什么？
② 决策边界：这是模型建议、代码规则，还是人工决定？
③ 质量边界：怎样用 Schema、证据和测试拦截错误？
④ 结果边界：怎样证明新版本更好，而不是只感觉更好？

你要练的不是“背模型原理”，而是能把业务问题画成数据流、说清每个交接契约，并用真实案例验证每个判断。
