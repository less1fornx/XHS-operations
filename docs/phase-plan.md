# 分阶段技术选型与原因

> 本文保留为阶段学习记录。最终技术架构、数据库设计、审查结论和执行顺序以 [architecture-final.md](architecture-final.md) 为准。

本项目的阶段设计遵循一个原则：先理解编排，再验证业务闭环，再增加模型能力，再增加真实数据和部署能力。每个阶段都保留人工控制点，避免在平台规则、数据来源和 Agent 质量都还不稳定时扩大自动化范围。

## 总体技术路线

```text
Phase 0  LangGraph 无模型实验
    -> Phase 1  本地骨架与假数据
    -> Phase 2  Agent 工作流与 LLM
    -> Phase 3  真实人工运营与合规数据入口
    -> Phase 4  本地模型替换与长期部署
```

| Phase | 核心问题 | 主要技术 | 阶段结果 |
|---|---|---|---|
| 0 | LangGraph 中各角色如何协作 | Python 3.12、LangGraph、假数据 | 理解 State、Node、Edge、Interrupt |
| 1 | 流程是否跑得通 | React、FastAPI、SQLite、数据库任务表 | 可操作的运营工作台 |
| 2 | Agent 是否真的有帮助 | LangGraph、结构化输出、LLM Provider | 可解释的筛选与起草 Agent |
| 3 | 能否安全地用于真实运营 | 人工录入、证据快照、Policy Gate、审计日志 | 可控的人工辅助运营系统 |
| 4 | 能否长期本地运行和替换模型 | Ollama、PostgreSQL、Redis、Docker Compose | 可迁移、可维护的本地部署系统 |

---

## Phase 0：LangGraph 无模型实验

### 要解决的问题

理解 LangGraph 的核心角色和流程控制，不让模型输出掩盖编排本身：

```text
State -> Node -> Edge -> Conditional Edge -> Interrupt -> Resume
```

### 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| Python | 3.12.14，范围 `>=3.12,<3.13` | 当前 LangGraph 版本要求 Python 3.10 以上；项目统一 3.12，避免 API、Worker 和实验之间切换运行时 |
| 环境管理 | 根目录 uv + 单一 `.venv` | 所有 Python 服务共用一个锁定环境，避免每个服务各自安装依赖产生冲突 |
| 编排 | LangGraph | 直接学习 StateGraph、节点、条件边、检查点和人工中断 |
| 数据 | TypedDict + 假店铺数据 | 先观察状态流转，不引入数据库、API 和模型变量 |
| 检查点 | MemorySaver | 在单进程实验中观察暂停和恢复；持久化数据库留到后续阶段 |

### 实验位置

```text
labs/phase0-langgraph/
├── pyproject.toml
├── run_demo.py
└── src/phase0_graph/lead_workflow.py
```

### 完成标准

- 能说清楚 State、Node、Edge、Conditional Edge 和 Interrupt 的区别。
- 能看懂 `trace` 中每个节点的执行顺序。
- 能让流程在 `human_review` 暂停。
- 能用 `Command(resume=...)` 恢复流程。
- 能自己修改一个节点，并预测状态变化。

完成 Phase 0 后再进入 Phase 1。Phase 0 的详细练习写在 [labs/phase0-langgraph/README.md](../labs/phase0-langgraph/README.md)。

## Phase 1：本地骨架与假数据

### 要解决的问题

先验证运营流程和页面交互，而不是先验证模型。需要确认你能否顺畅完成：

```text
查看店铺 -> 选择触达方式 -> 审核草稿 -> 查看风险 -> 打开官方页面 -> 记录结果
```

### 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 前端 | React + Vite + TypeScript | 启动快、结构直观，适合先学习页面状态和组件拆分 |
| UI | Tailwind CSS + shadcn/ui | 运营后台需要表格、抽屉、标签、弹窗、进度条和告警组件；这些组件可以直接改源码 |
| API | FastAPI | 自动生成 OpenAPI 文档，接口类型清楚，后续前端可以按契约调用 |
| 数据库 | SQLite + SQLModel | 单机部署不需要安装数据库服务，足以支撑第一阶段的假数据和小规模真实记录 |
| 任务执行 | SQLite 任务表 + Worker 轮询 | 暂时不引入 Redis，先把任务状态和重试逻辑看清楚 |
| 测试 | Pytest + 前端组件测试 | 先验证配额、状态机和关键组件，而不是追求大规模测试体系 |

### 为什么这样做

Phase 1 的核心是学习“业务状态如何流动”。如果一开始就接入消息队列、复杂数据库和真实平台数据，出现问题时很难判断是页面、API、数据库还是 Agent 导致的。SQLite 和假数据能让每一步都可观察、可重复。

### 第一阶段不做

- 不接真实小红书账号。
- 不自动采集全站数据。
- 不调用真实模型。
- 不实现自动发送。
- 不引入 Redis、PostgreSQL、Kubernetes 或复杂权限系统。

### 完成标准

- 可以创建店铺、视频证据和触达任务。
- 配额正确阻止第 6 个私信和第 4 个评论任务。
- 同一家店铺当天不能同时进入私信和评论队列。
- 风险状态变成 `FROZEN` 后，所有新触达按钮失效。
- 可以完整记录人工审核和发送结果。

## Phase 2：Agent 工作流与 LLM

### 要解决的问题

让 Agent 负责“分析和建议”，而不是直接控制发送动作：

```text
证据理解 -> 店铺评分 -> 选择触达方式 -> 起草 -> 风险检查 -> 等待人工审核
```

### 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| Agent 编排 | LangGraph | 工作流有明确节点、状态、分支和人工暂停点，比单次 Agent 对话更适合本项目 |
| 模型接口 | 自建 `LLMProvider` | 隔离 Qwen API、Mock 和未来本地 Qwen，避免业务代码绑定一个供应商 |
| 第一模型 | Qwen API | 中文 B2B 语境适配较好，并支持严格 JSON Schema 输出；与未来本地 Qwen 保持同一模型家族 |
| 输出格式 | Pydantic Schema / JSON Schema | 让评分、证据引用、风险原因和草稿都能被程序校验 |
| 提示词管理 | 版本化 Prompt 文件 | 每次生成都保存提示词版本，便于比较结果和复盘人工修改 |
| 评估 | 固定样例集 + 人工标注 | 用同一批店铺和视频比较模型版本，不凭感觉调模型 |

### 为什么这样做

Agent 应用的核心不是“让模型自由发挥”，而是让模型在明确的状态机和权限边界内完成任务。LangGraph 能把每个节点的输入、输出、失败和人工介入显式化，正好对应本项目的学习目标。

结构化输出也很重要。例如评分 Agent 不直接返回一段散文，而是返回：

```json
{
  "score": 82,
  "reasons": ["近30天有持续发布", "多次展示定制业务"],
  "evidence_ids": ["evidence_123"],
  "uncertainties": ["无法确认真实客单价"]
}
```

这样前端可以展示，API 可以校验，人工可以复盘。

### 第二阶段不做

- 不让 Agent 调用发送工具。
- 不让 Agent 自己决定突破配额。
- 不让 Agent 自动追发未回复对象。
- 不把模型的推测写成确定事实。

### 完成标准

- Agent 能引用具体证据生成店铺评分。
- 评论草稿能对应当前视频，而不是泛化广告文案。
- 私信草稿能说明联系依据和真实业务身份。
- 风险检查能拦截站外联系方式、重复内容和拒绝后的跟进。
- 人工修改率、误判率和证据引用准确率可以统计。

## Phase 3：真实人工运营与合规数据入口

### 要解决的问题

把假数据流程连接到真实工作，但仍然保留人工发送和人工确认：

```text
人工提供公开链接/截图
    -> 保存证据快照
    -> Agent 分析
    -> 人工审核
    -> 人工在官方页面操作
    -> 记录结果
```

### 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 数据入口 | 手动粘贴链接、文本和截图 | 第一版最容易确认来源和授权边界，不假设存在通用全站读取接口 |
| 文件存储 | 本地 `data/uploads` + 元数据表 | 保存证据快照，便于理解 Agent 的判断依据 |
| 内容解析 | 文本优先，图片 OCR 作为辅助 | 先减少视觉模型复杂度；无法确认的内容标记为不确定 |
| 业务规则 | 服务端 Policy Gate | 风险规则不能只放在前端，避免被绕过 |
| 审计 | AuditLog + RiskEvent | 每次生成、修改、批准、打开页面和结果都可追溯 |
| 发送方式 | 打开官方页面，人工操作 | 发送权限和平台反馈仍然由官方界面掌控 |
| 备份 | SQLite 定期备份 | 保护线索、证据和运营记录，成本低且适合本地运行 |

### 为什么这样做

真实运营阶段最重要的不是“自动化更多”，而是能解释每一个动作的来源和责任。保存证据快照可以防止视频删除或内容变化后无法复盘；服务端策略闸门可以防止前端误操作；人工记录结果可以逐步积累真实评估数据。

平台规则和开放能力可能变化，所以系统不把某个未经确认的接口当成核心依赖。以后若获得正式授权，只增加一个数据连接器，不改变领域模型和风险流程。

### 第三阶段不做

- 不使用非官方接口批量读取账号或笔记。
- 不自动模拟登录或绕过验证码。
- 不自动发送评论或私信。
- 不用多个账号轮换规避限制。
- 不把站外成交作为默认的私信模板目标。

### 完成标准

- 一条真实线索可以从证据录入走到人工发送结果。
- 可查看“这条草稿引用了哪些证据”。
- 发生发送失败或限制时，队列会冻结并产生告警。
- 能查看每日 5 条私信、3 条评论配额使用情况。
- 能导出店铺、证据、任务和审计记录。

## Phase 4：本地模型替换与长期部署

### 要解决的问题

让系统能稳定长期运行，并验证从云端 LLM 迁移到本地 Ollama 的成本和效果。

### 技术选型

| 领域 | 选择 | 原因 |
|---|---|---|
| 本地模型 | Ollama + `OllamaProvider` | 提供本地 OpenAI 兼容调用路径，便于替换模型而不改 Agent 业务代码 |
| 生产数据库 | PostgreSQL | 并发、索引、备份和查询能力比 SQLite 更适合长期数据 |
| 队列 | Redis + RQ/ARQ | Agent 任务、定时任务和失败重试不再依赖 API 进程轮询 |
| 部署 | Docker Compose | 本地部署多个服务时，环境更一致，启动和备份更容易 |
| 观测 | 结构化日志 + 健康检查 | 区分 API、Worker、数据库、模型和外部服务的问题 |
| 迁移 | Alembic | 数据库表结构变化可追踪、可回滚 |

### 为什么不是第一阶段就用 Ollama

本地模型的价值主要在隐私、成本和离线能力，但它会引入模型下载、内存、速度、中文质量和结构化输出稳定性等变量。先用稳定模型验证 Agent 节点和业务规则，等你知道“模型需要完成什么”之后，再对比 Ollama 的质量和资源消耗，学习效率更高。

### 迁移策略

同一份评估样例分别跑：

```text
QwenProvider -> 云端质量基线
OllamaProvider（本地 Qwen） -> 成本、速度、隐私和质量对比
```

只有在结构化输出合格、风险拦截不下降、人工修改率可接受时，才把本地模型设为默认。

### 完成标准

- Docker Compose 可以启动 Web、API、Worker、PostgreSQL 和 Redis。
- Qwen API 与本地 Qwen 可以通过配置切换。
- 任务失败可以重试，且不会重复生成外部发送动作。
- 数据库可以备份和恢复。
- 能查看模型版本、Prompt 版本和任务耗时。

---

## 选择顺序背后的原则

1. 先流程，后模型：没有稳定流程，模型好坏无法判断。
2. 先人工，后自动化：人工审核数据本身就是 Agent 的评估集。
3. 先本地简单部署，后分布式基础设施：复杂度应由真实瓶颈推动。
4. 先抽象接口，后替换供应商：业务逻辑不绑定 Qwen API 或 Ollama。
5. 先记录证据，后追求规模：运营系统最重要的是可解释、可追溯和可暂停。
