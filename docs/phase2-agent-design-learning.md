# Phase 2：Agent 设计学习与实践

这份文档不是 API 使用说明，而是本项目的 Agent 设计学习主线。目标是让你能够解释、修改和评估系统，而不是只会更换模型名称。

## 1. 先理解完整链路

```text
业务事实与证据
    -> Context Builder
    -> Versioned Prompt
    -> LLM Provider
    -> Pydantic Structured Output(Python的结构化输出组件)
    -> Evidence Validator
    -> Code Policy Gate
    -> Human Review
    -> Outcome Feedback
    -> Evaluation / Strategy Version
```

每层只解决一个问题：

| 层 | 解决的问题 | 不能承担的职责 |
|---|---|---|
| Context | 模型本次能看到什么 | 不能把推测包装成事实 |
| Prompt | 告诉模型任务、边界和方法 | 不能代替程序校验和权限控制 |
| Provider | 隔离 Qwen、Mock 和未来 Ollama | 不能包含业务判断 |
| Schema | 让输出可验证、可展示、可评测 | 不能保证内容事实正确 |
| Evidence Validator | 检查引用是否真实存在 | 不能判断文案是否自然 |
| Policy Gate | 拦截导流、追发和评论销售招揽 | 不能负责创作文案 |
| Human Review | 承担最终业务决定 | 不能绕过 Policy Gate |
| Evaluation | 比较版本是否真的改善 | 不能只看一个“感觉不错”的案例 |

## 2. 为什么第一版使用一个 Agent 调用

第一版把店铺摘要、路线建议和草稿放在一次结构化调用中，原因是案例少、成本低、方便观察完整输入输出。但输出字段已经按职责分开。以后只有在评测证明某一环节经常互相干扰时，才拆成 EvidenceExtractor、RouteAdvisor 和 Drafter 多次调用。

这是成熟 Agent 设计的重要原则：先做可评测的最小工作流，再用数据决定是否增加 Agent 数量，而不是先搭建“多 Agent 群聊”。

## 3. 你在 Phase 2 必须亲自参与的四件事

### 3.1 审查输入上下文

查看 `LeadAgentInput`，判断每个字段是否是模型做决策真正需要的事实。重点检查：

- 是否把人工结论误当成原始事实。
- 是否把成交后信息泄漏给联系前的筛选流程。
- 是否存在模型根本不需要看到的个人信息。

### 3.2 审查 Prompt 规则

阅读 `prompts/lead_outreach/v1/system.md`，逐条判断：

- 这条是稳定业务规则，还是暂时策略？
- 应由 Prompt 控制，还是必须由代码硬拦截？
- 是否有正例和反例能够验证它？

### 3.3 标注固定案例

每个案例至少给出：真实输入、期望路线、必须包含、禁止包含。案例的作用不是教模型背答案，而是比较 Prompt 和模型版本。

### 3.4 阅读评测报告

第一版关注四项指标：

- `route_accuracy`：路线是否和人工判断一致。
- 证据引用有效性：是否引用不存在的 evidence_id。
- 必须信息覆盖率：个性化依据和真实产品事实是否出现。
- 禁止内容命中：是否出现导流、追发或评论销售表达。

后续真实运营再增加人工修改率、正向回复率和成交率。不同阶段的指标不能混在一起。

## 4. 你的当前操作

1. 暂时保持 `.env` 中 `AGENT_LLM_PROVIDER=mock`，先运行无成本评测并查看每个案例。
2. 阅读第一版 Prompt，把不符合真实业务的句子逐条指出，而不是直接说“效果不好”。
3. 在评估表中补充 5 个案例；真实成交反馈目前可以为空。
4. 准备使用 Qwen 时，在本机 `.env` 填写 `DASHSCOPE_API_KEY`，不要把 Key 发到聊天、代码或截图中。
5. 用同一批案例分别运行 mock 和 Qwen，比较报告后再修改 Prompt。

## 5. 当前明确不做

- 不用真实运营结果直接训练或微调模型。
- 不让模型自己修改 Prompt、配额或安全规则。
- 不以单个成功案例证明某种筛选规律。
- 不把输出流畅度当成事实准确性。
- 不在没有固定评估集时更换默认模型。

## 6. 你最终需要掌握的 Agent 设计能力

本项目把学习目标分成五层。每一层都要能回答“为什么”，而不只是会运行命令。

| 层级 | 需要掌握 | 本项目中的实物 |
|---|---|---|
| 1. 业务建模 | 把目标、状态、权限和失败情况说清楚 | DM/comment/reject、人工审核、勿扰名单、每日配额 |
| 2. 上下文工程 | 决定模型看什么、不看什么，区分事实和推测 | `LeadAgentInput`、`evidence_id`、联系前特征快照 |
| 3. Prompt 与契约 | 写清任务步骤，并用 Schema 限制可返回的结构 | `system.md`、`LeadAgentOutput` |
| 4. 编排与护栏 | 区分模型判断、代码规则、人工决策和外部动作 | LangGraph、Policy Gate、Human Review |
| 5. 评估与迭代 | 用固定案例、真实反馈和版本对照证明改动有效 | `phase2_cases.v1.json`、评测报告、策略版本 |

### 6.1 四种职责不能混在一起

```text
模型：理解语义、归纳证据、生成候选内容
代码：校验结构、配额、状态、禁止项和幂等
人工：确认业务判断、修改文案、执行平台动作
数据：保存输入、版本、决策和结果，支持后续评估
```

如果一个需求出现，先判断它属于哪一类。例如“已读未回不能再次进入候选”是确定性规则，应写进代码；“这家店最近可能在找春夏内搭”是语义判断，可以交给模型，但必须附证据并由人工确认。

### 6.2 Phase 2 的学习验收

进入 Phase 2B 前，你应能用自己的话回答：

1. 为什么不能只让模型输出一段自然语言？
2. Prompt 规则和代码硬规则有什么区别？
3. `evidence_ref` 如何降低模型编造事实的风险？
4. 为什么 Mock Provider 不是正式模型，却仍然有价值？
5. 为什么修改 Prompt 后必须重跑同一批案例？
6. 为什么 LangGraph 负责编排，却不能代替业务数据库？

这些问题的答案会直接影响下一步的节点设计、调用记录和人工审核页面，而不是额外的理论作业。
