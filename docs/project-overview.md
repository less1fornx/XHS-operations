# 项目总览

更新：2026-10-03。本文描述项目当前的真实状态，供用户通读。需求以 `project-memory.md` 为准，后续安排见 `roadmap-and-learning.md`。

## 1. 这是什么

一个在本机运行的获客工作台：帮毛衫工厂在小红书上筛选西装定制店，为每家店起草首次私信或评论，并记录对方的反应。

- 我方：可做高端品质的毛衫工厂，为西装定制店提供西装内搭，款式不限，一件起订。
- 对象：活跃、注重面料、客单价中高的西装定制店。
- 系统做的事：读店、筛店、起草、提醒、记录。
- 系统不做的事：不登录小红书、不抓取、不发送。发送由人在小红书里完成。

## 2. 业务流

```text
① 你在小红书里看店，截图（每家 1 到 3 张，至少一张主页）
        ↓ 上传，每批最多 10 家
② 系统读图：摘抄简介、价格、面料、门店、笔记日期（模型）
        ↓
③ 系统分档：高 / 中 / 低 / 排除，并按当日配额建议私信或评论（程序规则 v0）
        ↓
④ 你整批审核一次：改正认错的类型、调整路线、标注“同意 / 不同意”
        ↓
⑤ 系统为入选的店起草私信或评论（模型）
        ↓ 策略检查：站外导流、评论里的销售话术（程序）
⑥ 你审核文案：修改、驳回，或通过
        ↓ 再做一次策略检查（程序）
⑦ “现在去发”或“定时提醒”：系统复制文案、打开对方页面或搜索页
        ↓
⑧ 你在小红书里粘贴、发送，回来点“已发送成功”
        ↓ 系统保存联系时快照
⑨ 对方回复后，你上传私信截图或粘贴原话；系统读出原话并建议标签
        ↓
⑩ 你确认标签、选择进展阶段；15 天没回复自动结束
```

另有一条手动入口：没有截图时，直接填写店铺信息，从第 ⑤ 步开始。

## 3. 谁在做判断

这是整个设计的核心：三类判断者各管一段，互不越界。

| 判断者 | 负责什么 | 例子 |
|---|---|---|
| 模型（Qwen） | 看和写：读截图、摘抄原文、起草文案、给对方回复打建议标签 | “简介里写了全麻衬”“这条私信怎么开头” |
| 程序规则 | 所有确定的事：分档、排序、配额、勿扰、策略拦截、时效 | “满足两项信号且含面料算高匹配”“15 天没回复就结束” |
| 人 | 所有最终决定：联系谁、发什么、对方走到哪一步 | 审核名单、修改文案、判断阶段 |

原则：能用规则写清楚的不交给模型；会产生实际后果的必须经过人。

## 4. 架构

```text
浏览器（React 页面）
   │  HTTP
   ▼
后台 API（FastAPI）
   ├── 规则层：分档、勿扰、策略检查、配额、时效
   ├── 编排层（LangGraph）
   │      ├── 批量初筛流程：并行读图 → 排序 → 等人审核
   │      └── 单店起草流程：模型建议 → 等人选路线 → 起草 → 检查 → 等人审文案
   ├── 模型层：统一入口，可切换 Qwen 或 Mock
   └── 数据层（SQLite）：业务表、模型调用记录、流程断点

后台轮询进程（Worker）：到点提醒、超时结束、清理过期截图
```

| 层 | 职责 | 主要代码 |
|---|---|---|
| 页面 | 上传、审核、发送确认、记录回复 | `apps/web/src/App.tsx`、`Screening.tsx`、`Reply.tsx` |
| API | 接收操作、校验状态、调用编排、保存结果 | `services/api/app/main.py` |
| 规则 | 不依赖模型的确定性判断 | `packages/agent_core/screening.py`、`outcomes.py`、`contracts.py` |
| 编排 | 步骤顺序、并行、人工停点 | `services/worker/screening_graph.py`、`labs/phase0-langgraph/src/phase0_graph/lead_workflow.py` |
| 上下文 | 把店铺信息和产品事实整理成模型输入 | `services/worker/lead_generation.py` |
| 模型 | 调用 Qwen，校验输出格式 | `packages/agent_core/providers.py`、`vision.py`、`pipeline.py` |
| 数据 | 表结构、读写、迁移 | `services/api/app/models.py`、`storage.py`、`alembic/` |

## 5. 两条编排流程

### 批量初筛

```text
开始 ──分发──► 读店铺 A ─┐
            ├► 读店铺 B ─┼─► 排序（规则 v0）─► 暂停：等你审核 ─► 结束
            └► 读店铺 C ─┘
```

- 每家店独立读取，同时进行；一家失败不影响其他家。
- 用到的 LangGraph 概念：`Send`（分发）、列表合并、`interrupt`（暂停等人）。

### 单店起草

```text
开始 ─► 模型建议 ─┬─ 勿扰名单 ─► 结束
                 └─► 暂停：等你选路线 ─┬─ 暂不触达 ─► 结束
                                      └─► 起草 ─► 策略检查 ─┬─ 命中 ─► 拦截
                                                          └─► 暂停：等你审文案 ─► 再次检查 ─► 加入提醒
```

- 你选的路线和模型建议不同时，按你选的路线重新起草。
- 模型调用失败也会交给你决定，不会自动结束。
- 每个暂停点的状态都存进数据库，后台重启后可以继续。

## 6. 模型看到什么（上下文）

| 调用 | 输入 | 输出 | Prompt |
|---|---|---|---|
| 读店铺截图 | 1 到 3 张图 | 原样摘抄的字段，以及哪些字段看不清 | `prompts/shop_extraction/v1` |
| 起草 | 店铺情况、笔记标题、带编号的证据、产品事实、人工选定的路线 | 路线建议、理由、个性化依据（标明出自哪条证据）、草稿、不确定的地方 | `prompts/lead_outreach/v4` |
| 读私信截图 | 1 到 3 张图 | 对方原话、建议标签、是否出现联系方式 | `prompts/reply_extraction/v1` |

产品事实单独放在 `config/product_facts.v2.json`，不写死在 Prompt 里。模型只能引用其中的内容。

## 7. 规则清单

| 规则 | 内容 | 位置 |
|---|---|---|
| 分档 v0 | 前提是西装定制店；信号为活跃、注重面料、高客单价、实体门店；高档需至少两项且含面料或客单价；置顶笔记不算活跃 | `screening.py` |
| 配额 | 每日私信 5 家、评论 3 家，同一店同一天只走一条路线 | `storage.py` |
| 勿扰 | 已拒绝、已读不回、被拉黑、15 天未回复的店不再联系 | `contracts.py`、`storage.py` |
| 策略检查 | 文案出现微信、二维码、手机号、网址、“看主页”等即拦截；评论出现供货、报价、一件起订等即拦截 | `lead_workflow.py` |
| 回复时效 | 3 天内正常，3 到 15 天迟回复，15 天未回复自动结束 | `outcomes.py` |
| 超时 | 等你审核超过 48 小时自动结束；截图原图保存 10 天 | `storage.py`、`screening.py` |

## 8. 数据

共 16 张表，分四类：

| 类别 | 表 | 存什么 |
|---|---|---|
| 业务主体 | `shop_leads`、`content_evidence`、`outreach_tasks`、`screening_batches` | 店铺、证据、每次触达任务、每批初筛结果和你的标注 |
| 结果 | `contact_snapshots`、`outreach_outcomes` | 发送当时的分档、信号、版本和文案；对方的回复、标签、阶段 |
| 过程 | `workflow_runs`、`run_snapshots`、`run_events`、`model_invocations`、`human_reviews` | 流程状态、每次模型调用的输入输出和耗时、你的每次审核 |
| 管控 | `platform_accounts`、`quota_usage`、`risk_events`、`audit_logs`、`product_offers` | 账号状态、配额、风险事件、操作留痕 |

另有一个独立文件保存 LangGraph 的流程断点。

不进数据库的内容：密钥、电话和微信号、私信截图。

## 9. 技术栈与选型理由

| 部分 | 选型 | 为什么 |
|---|---|---|
| 页面 | React 19、Vite 8、TypeScript | 常见组合，本机启动快 |
| 后台 | Python 3.12、FastAPI | Agent 生态以 Python 为主 |
| 编排 | LangGraph 1.2 | 流程显式可见，支持暂停等人和断点恢复 |
| 模型 | 通义千问 `qwen3.7-plus`，经阿里云百炼调用 | 国内可用，同一个模型既能读图又能写文案；以后可换成本地 Qwen |
| 模型抽象 | 自定义 `LLMProvider` 接口，带 Mock 实现 | 换模型不改业务代码；测试不花钱 |
| 输出校验 | Pydantic | 模型输出格式不对直接判失败，不让错误往下传 |
| 数据库 | SQLite、SQLModel、Alembic | 本机零配置；表结构变更有版本、可回退；以后迁移 PostgreSQL |
| 版本管理 | Git，仅本机 | 未绑定任何远程仓库 |

## 10. 能力边界

**能做**

- 从截图读出店铺信息，区分置顶和非置顶笔记，识别非店铺截图。
- 按规则分档并说明每一项依据。
- 针对每家店的具体内容起草私信或评论。
- 拦截站外导流和评论中的销售话术。
- 一键复制文案并打开对方页面或搜索页。
- 记录回复、标签、阶段和联系时快照。

**不做（设计上的边界）**

- 不自动登录、不自动浏览、不抓取小红书。
- 不自动发送私信或评论。
- 不生成规避平台检测的内容（号码拆分、谐音、图片藏号码等）。
- 不保存联系方式和私信截图。

**目前做不到或有限制**

- 读不了视频，只能读截图。
- 截图里看不到的信息只能记为未知，例如多数店不在主页标价。
- 模型偶尔认错店铺类型，需要你在审核时改正。
- 分档规则 v0 没有经过真实数据验证。
- 模型不会从使用中自己学习，改进要靠人改规则或 Prompt。
- 评测考卷只有 6 题，且多数是拟真案例。
- 没有汇总指标和周期分析。
- 只支持一个账号、单机使用。

## 11. 当前验证状态

- 自动测试 49 项通过。
- Qwen 固定案例评测 6/6 通过，其中只有 3 题真正调用了模型，不能当作准确率。
- 截图初筛、起草、发送确认、回复记录都用真实 Qwen 或浏览器走通过。
- 真实业务数据还很少：真实发送过的店铺只有个位数。
